# QQ 双向聊天

把 QQ 接成一条对话通道：QQ 里有人说话，App 转给模型，回答自动发回去。

```
QQ ←→ NapCat / SnowLuma（手机 Termux 里跑）←HTTP→ DSH Watch ←→ 模型
```

不经过任何第三方服务器：后端在本机回环（`127.0.0.1`）上，消息不出这台手机。

## 为什么需要一个后端

QQ 的登录协议由腾讯把守，任何第三方实现都要逆向 + 持续对抗风控。事实标准是
**OneBot 11**：NapCat / SnowLuma 这类后端负责登录与协议，对外只暴露一组 HTTP 接口。
DSH Watch 只跟这组接口说话，不碰 QQ 协议本身。

## 直连登录（不用后端）

设置 → QQ 消息 → **直连登录**。这条路上 App 自己就是 QQ 客户端，不需要 NapCat。

用的是**官方 QQ 手表版**（`com.tencent.qqlite`）的身份：它走 SSO v5，
登录包不需要 `qsign` 那种签名服务，所以能纯本地算出来。链路上只有公开的密码学：

> 版本号报的是官方手表版**当前版本（9.0.1 / SDK 6.0.0.2498）**。老版本（2.0.8）
> 取码、扫码、确认都还能走，只有在换票那一步被服务端按「过期客户端」打回 45，
> 而且不给任何解释。签名摘要仍用老的那一份 —— 官方 9.0.1 这一版换成了 NT 内核
> （libfekit），native 里做校验，服务端对它并不比对新旧签名，真正卡的是版本。
>
> 注意：官方 9.0.1 的登录包里还带 **0x544 签名 TLV**（secprotocol，由 libfekit
> 现算）。我们这条 SSO v5 链路发不出这一段，如果版本号改到 9.0.1 之后仍然回 45，
> 说明服务端要的就是 0x544，那纯 Kotlin 这条路就走不通了。

| 层 | 做法 |
|---|---|
| 密钥交换 | P-256 ECDH，公钥随包发出，共享密钥取 X 坐标前 16 字节的 MD5 |
| 传输加密 | TEA（16 轮），外层用全 0 密钥，内层用协商密钥 |
| 登录命令 | `wtlogin.trans_emp`，子命令 `0x31` 取码、`0x12` 查状态 |
| 换票 | `wtlogin.login`（24 条 TLV），拿回 A2 / D2 / D2Key / ksid / tgt |
| 重连认证 | `wtlogin.exchange_emp` 子命令 11，用保存的 tgt 重新认证长连接 |
| 上线注册 | `StatSvc.register`，**0x0A 包**（登录型）、JCE/Tars 正文、外层带 d2；不做这一步，业务包一律回 -10008 |
| 心跳 | `Heartbeat.Alive`，0x0A 包、不加密 |
| 收发消息 | `MessageSvc.PbGetMsg` / `PbSendMsg`，0x0B 包、d2Key 加密 |

**现在能到哪一步**：出二维码 → 扫码确认 → 换票 → 登录态加密落盘（重启不用重扫）
→ 建长连接 → 换票认证 → 上线注册 → 心跳 → 取私聊 → 发私聊。

设置页的「连接自检」会逐步跑完这四步并给出耗时；配置了「对方 QQ 号」时，
它还会自动发一条「DSH 连接测试」，用来验证发送链路。

还没做的：群消息、图片/表情、语音、长消息分片、断线自动重连（目前是一次性连接，
断了要重新点自检）。日常聊天在补齐这些之前仍建议用上面那套 OneBot 方案。

失败时会给具体原因和返回码，而不是一个数字：要图形验证码（2）、账号被冻结（40）、
当前客户端不允许登录（45）、需要短信验证（160 / 239）、设备校验不过（204）。

> **风控提醒**：扫码成功后，你的手机会显示这个号「QQ手表在线」，部分账号会被
> 直接拒绝（返回码 45）。**先用小号试**，别拿主号赌。

### 手机上说「未识别到设备名称」

不是协议算错了，是取码请求里那一段设备名报了空：二维码照样能出、能扫，一路到
「已确认」都正常，只有手机点确认那一瞬间才被挡 —— 服务端要先知道「这是台什么设备」
才肯放行，拿不到名字就要求检验身份，随后把这次登录判成风控，客户端只看到一个 45。

现在报的是 `品牌 + 机型`，与 0x144 里的机型、0x16e 同一份，见 `DeviceProfile.deviceName`。
这一项一直为空的话，重装、换 guid 都不会好。

还有一种情况改代码解决不了：**账号本身在被风控**。新注册的号、长期没登录的号、
异地首次登录，服务端就是要拦，和设备名填得对不对无关。这种只能先用正常客户端在
这台手机上连续登录几天，或者换个小号。

### 票据解密用的那把 key

登录包的 0x144 用 tgtgtKey 加密、换回来的 0x119 用同一把解 —— 但**必须是服务端
在「已确认」时用 0x1e 下发的那一份**，不是本地按 guid 派生的。用错了表现为
「包发出去了，响应解不开」，比 45 更难查：0x144 能加出去，0x119 就是一团乱码。

### 响应正文为什么解不开

自检卡在第二步、报 `EOFException: Unexpected end of ZLIB input stream` 时，
问题不在压缩算法，在**切数据的刀口**。响应的 SSO 头是这样：

```
[4 头长度][4 序号][4 返回码][lv32 额外数据][lv32 命令名][lv32 会话 id][4 压缩标志]
[4 正文长度][正文]
```

看起来可以顺着 `readLv32()` 一路读下去，但这段结构**字段个数在服务端版本之间会变**
（多一段少一段都出现过），一旦错位，压缩标志读到的是随机字节，正文长度读到的是正文里的
某 4 字节 —— 切出来的 zlib 流自然短一截，报的却是「流没读完」。

现在的做法是三条都不靠顺序：

| 项目 | 依据 |
|---|---|
| 外层密文起点 | 登录型（0x0A）`[1 标志][lv32 uin]`；业务型（0x0B）`[4 序号][1 标志][lv32 uin]`。两种都试，都不对就按「密文必为 8 字节倍数」扫偏移 |
| 正文起点 | 头长度字段 `[0]`，正文严格从 `headerLen` 开始 |
| 命令名 | 在头内扫「可见 ASCII 且带点/下划线」的 lv32 段，长度不可信就滑 1 字节重试 |
| 是否压缩 | 正文首字节：`0x78` 是 zlib、`0x1F 8B` 是 gzip。JCE / protobuf 的首字节是 tag，从 0x08 这种小值起，撞不上 |
| 正文长度 | 含自身（`len-4`）、不含自身（`len`）、直到包尾，三种切法依次试解压 |
| 解密变体 | 每个切法再试「按 8 字节截齐」（尾部多写了几字节）与「零钥」（头部写 `0x01` 实际用全 0 密钥） |

外层这一条踩过两次，症状完全不同但同源：

- **0x0B 响应少算 4 字节**：把外层的随机序号当成了 uin 段的长度，报
  「包长度不够：还差 17855240 字节，只剩 4215」—— 那个 17855240 就是序号本身。
- **正文长度口径**：请求侧含自身 4 字节（服务端认），响应侧按不含自身写。
  照抄请求的习惯就少读 4 字节，zlib 流缺尾，报 `Unexpected end of ZLIB input stream`。

还有一条与协议无关、纯粹是代码写法的坑：**多候选解析必须逐个 `runCatching`**。
第一版把「切法 A 失败」直接抛出，后面的切法 B、C 和偏移扫描永远没轮到执行，
表现出来就是「明明加了三种切法，还是报第一刀的错误」。候选列表的意义在于
「谁对用谁」，那么每个候选的失败都必须被吞掉。

同理，等响应时**认不出的包不能直接返回给调用方**：它可能是尚未支持的推送，
调用方拿去二次解析只会把同一个错再抛一遍。正确做法是记下原始字节继续等，
等超时才连同十六进制一起报出来 —— 那时的错才是有信息量的。

两个错都不会说「长度不对」，只会说「读不完」。所以现在解析失败时会把原始包的
前 80 字节十六进制一起抛出来 —— 没有这串字节，任何进一步猜测都是浪费一轮安装。

### register 回包的两层意外

`StatSvc.register` 发得对、包也解开了，仍然可能卡在 ②，有两个原因：

1. **回包之前先来了推送**。服务端在 exchange 成功后就认为你上线了，立刻推
   OnlinePush / ConfigPush，这些包同样是「SSO 码 0、有正文」，4KB 上下。
   按「下一个包就是答案」去读，拿到的是推送内容，交给 JCE 解析器就会乱跳。
   现在按**命令名**挑回包（命令名为空的版本视为匹配，不能死等）。
2. **回包本身是 oicq 包装**：`[02][2 包长][2 版本][2 命令号][2 序号][4 uin]…[03]`。
   首字节 0x02 会被 JCE 当成「tag 0、类型 INT」，接着读到的 4 字节是包长
   （`01 10 …`），于是报「还差 17850632 字节」—— 那个数字是 272 字节的包长
   乘出来的。现在先试 `peelOicq`，拆出来的内容能被 JCE 解析才采用。

### `sBuffer` 不是裸结构，是版本 3 的表

这一坑更难查，因为**服务端不会回错误码，它什么都不回** —— 自检里表现为
「等 StatSvc.register 超时，期间一个包都没收到」，看起来像网络问题或包型错。

```
RequestPacket {
  sBuffer = RequestDataVersion3 {           // ← 少了这一层
    "SvcReqRegister" -> 0x0A <SvcReqRegister> 0x0B
  }
}
```

`0x0A … 0x0B` 是结构体的起止标记（Tars 的 STRUCT_BEGIN / END），
`0x08` 是「tag 0、类型 8（map）」的头，后面跟 4 字节元素个数。

响应同一个道理，而且**版本 2 和 3 都会出现**：版本 3 的表值是 `byte[]`，
版本 2 的是「表里再套一层表」。所以读响应要两版都试，剥到 `0x0A … 0x0B`
之后还要再校验里面第一个字段是 tag 0 的整数（uin）——
只比首尾两字节的话，protobuf 正文（字段 1 的头恰好就是 `0x0A`）会被误认成回包，
于是「登记成功」但后面取消息一直 -10008。


## 在手机上跑后端（Termux）

以 NapCat 为例，Termux 里大致是这几步（不同版本命令略有差异，以官方文档为准）：

```bash
pkg update && pkg install nodejs-lts git
# 按 NapCat 文档安装，首次启动会给出一个二维码
# 用手机 QQ 扫码登录（注意：登录后手机 QQ 本体可能被挤下线）
```

然后在 NapCat 的配置里打开 **HTTP 服务**：

- 监听地址：`127.0.0.1`（只给本机用；填 `0.0.0.0` 表示局域网也能访问）
- 端口：`3000`
- `access_token`：可以留空，也可以设一个，再填到 App 里

验证一下：

```bash
curl -s http://127.0.0.1:3000/get_login_info
# {"status":"ok","retcode":0,"data":{"user_id":123456,"nickname":"..."}}
```

有这段返回就说明通了。

> **Termux 保活**：Android 会杀后台。要给 Termux 关电池优化，并在通知栏常驻它的
> 前台会话。否则 App 这边会一直报「连不上」—— 其实是后端被系统停了。

## App 里怎么配

设置 → **QQ 消息**：

| 项 | 说明 |
|---|---|
| 总开关 | 打开后启动一个前台服务常驻轮询，通知栏会显示连接状态 |
| 地址 | 默认 `http://127.0.0.1:3000`；后端在电脑上时填 `http://192.168.x.x:3000` |
| 访问令牌 | 后端设了 `access_token` 就填一样的内容 |
| 我的 QQ 号 | 留空则启动时自动问后端要（`get_login_info`） |
| 测试连接 | 调一次 `get_login_info`，把后端自己的原话弹出来 —— 连不上时先按这个 |
| 私聊 · 对方 QQ 号 | **必填。** 只处理这一个人发来的消息 |
| 群聊 · 群号 | 群消息的入口 |
| 必须 @ 我 | 群里默认只有 @、引用我、或命中前缀才回 |
| 触发前缀 | 逗号分隔，例如 `小D,ds`；效果等同被 @ |
| 轮询间隔 | 默认 4 秒。越小越跟手，也越费电 |

## 触发规则

| 场景 | 会不会回 |
|---|---|
| 私聊 | 配了对方 QQ 号就回 |
| 群聊 · 被 @ | 回 |
| 群聊 · 引用我说过的消息 | 回（群里很多人不用 @，长按引用代替） |
| 群聊 · 命中前缀 | 回，前缀本身会被去掉再交给模型 |
| 群聊 · 只是普通发言 | 不回（除非关掉「必须 @ 我」） |
| 自己发出去的消息 | 永远不回（按 `self_id` 过滤） |

## 保活与开机自启

App 这边用的是**前台服务**（`specialUse` 类型）。选它不是为了「更高级」：

- `dataSync` 在 Android 15 上每个应用每 24 小时只有 6 小时额度，到点系统会直接
  结束服务 —— 一个「一直挂着等消息」的功能用 `dataSync` 注定半天就断；
- `specialUse` 没有这个额度，代价是需要在清单里写一行用途说明。

另外两处会自己把服务拉起来，不用手动点开 App：

- 开机、以及覆盖安装新版本之后（装包会杀掉服务）；
- 每次 App 回到前台时补一次（服务被系统杀掉后进程是新的，不补就一直显示
  「已连接」但一条消息都不进来）。

厂商省电策略仍可能把 App 一起冻掉。如果发现「锁屏久了就不回」，给本 App 关掉
电池优化（设置里搜「电池优化」→ 找到 DSH Watch → 不优化）。

## 它长什么样

每条 QQ 会话在 App 的会话列表里是一个独立会话，标题是「QQ 张三」或「QQ 群 123456」。
可以直接进去接着聊，历史与 QQ 那边是同一份 —— 你在 App 里补一句，模型看到的上下文是连续的。

图片：对方发的图会下载到应用私有目录（`files/qq/media`），作为多模态输入一起交给模型
（单条最多 3 张、单张 8 MB）。模型回复里的纯文字会被发回去；回复里的图片暂不转发。

## 安全边界

- **回复不带任何工具能力。** QQ 消息可能来自群里的任何人，不能让它在你手机上装应用、
  改设置或读文件。这个实例是独立构造的，`forceAgentOff` 写死在容器里，设置里也关不掉。
- 地址默认回环。填公网地址能用，但那意味着聊天内容要过一次别人的机器。
- 令牌明文存在设置里 —— 它保护的是本机回环，泄露面等于「谁能碰你手机」。

## 常见问题

**连不上（提示 ConnectException）**
后端没起、端口不对，或者 Termux 被系统杀了。先在 Termux 里 `curl` 一次。

**连上了但群里 @ 了不回**
先看设置里的「登录账号」有没有拿到号码 —— 拿不到就没法判断「@ 的是不是我」。
再确认群号填的是群号，不是某个人的 QQ 号。

**一开开关就刷了一屏历史**
不应该发生。桥接第一次看到某个会话时只记位置、不回复。如果真出现了，
说明 cursor 文件被清掉（`files/qq/cursor.json`），删掉重开即可。

**回复重复**
去重靠 `message_id`。如果后端每次返回的 id 都在变（少数魔改版），会重复。
换官方 NapCat 或 SnowLuma。

**很费电**
轮询本身很轻（一次 HTTP 往返），大头是 Termux 里的 Node 常驻。
不想用时把总开关关掉，服务和轮询会一起停。
